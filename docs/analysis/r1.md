# 요구사항 정의서

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | ticketing |
| 목적 | 콘서트 티켓 예매 상황(짧은 시간에 트래픽 집중)에서 발생하는 **동시성 문제**를 직접 재현하고, 대기열·분산락·낙관적 락 등으로 해결해보는 학습용 프로젝트 |
| 핵심 시나리오 | 대기열 진입 → 좌석 임시선점 → 결제 → 예약 확정 |
| 대상 사용자 | 일반 사용자(예매자), 관리자(공연/좌석 등록) |
| 범위 제외 | 실제 PG 결제 연동(모의 결제로 대체) |

<br>

## 2. 기능 요구사항

### 2.1 회원

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-01 | 회원가입 | 이메일, 비밀번호, 이름으로 가입. 이메일 중복 불가 | 필수 |
| FR-02 | 로그인 | 이메일/비밀번호 인증 후 인증 토큰(JWT) 발급 | 필수 |
| FR-03 | 내 정보 조회 | 로그인한 사용자의 기본 정보 조회 | 선택 |

### 2.2 공연

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-10 | 공연 목록 조회 | 예매 가능한 공연 목록을 페이징으로 조회 | 필수 |
| FR-11 | 공연 상세 조회 | 공연 정보 + 회차 목록 조회 | 필수 |
| FR-12 | 회차별 좌석 조회 | 특정 회차의 좌석 목록과 상태(AVAILABLE/HELD/SOLD) 조회 | 필수 |
| FR-13 | 공연/회차/좌석 등록 | ADMIN 권한 사용자가 공연, 회차, 좌석을 등록 | 필수 |

### 2.3 대기열

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-20 | 대기열 진입 | 사용자가 특정 회차 예매 대기열에 진입하면 대기열 토큰 발급 | 필수 |
| FR-21 | 대기 순번 조회 | 내 앞에 몇 명이 있는지, 예상 대기 시간 조회 | 필수 |
| FR-22 | 활성 전환 | 회차별 활성 사용자 수가 정원 미만이면 대기 중인 사용자를 순서대로 활성 상태로 전환 | 필수 |
| FR-23 | 대기열 토큰 만료 | 활성 상태에서 일정 시간(예: 10분) 예매를 완료하지 못하면 대기열 토큰 만료. 만료 시 해당 사용자의 HELD 예약도 즉시 EXPIRED 처리하고 좌석을 AVAILABLE로 복구 | 필수 |
| FR-24 | 대기열 토큰 검증 | 좌석 선점/결제 API 호출 시 유효한 활성 대기열 토큰인지 검증 | 필수 |
| FR-25 | 활성 슬롯 반환 | 결제 완료, 예약 취소, 대기열 토큰 만료 시 활성 슬롯을 반환하고 다음 대기자를 활성 전환(FR-22) | 필수 |

### 2.4 예약

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-30 | 좌석 임시선점 | AVAILABLE 좌석을 선택하면 HELD 상태로 전환하고 예약(HELD) 생성. TTL 5분 | 필수 |
| FR-31 | 중복 선점 방지 | 동일 좌석에 동시 요청 시 한 명만 성공, 나머지는 실패 응답 | 필수 |
| FR-32 | 선점 만료 처리 | TTL 내 결제되지 않으면 좌석을 AVAILABLE로 복구하고 예약을 EXPIRED 처리 | 필수 |
| FR-33 | 예약 취소 | 사용자가 HELD/CONFIRMED 예약을 취소하면 좌석 복구. CONFIRMED 취소 시 환불(FR-43) 연계 | 필수 |
| FR-34 | 예약 내역 조회 | 내 예약 목록 및 상세 조회 | 선택 |

### 2.5 결제

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-40 | 결제 요청 | HELD 상태 예약에 대해 결제 요청. 성공 시 예약 CONFIRMED, 좌석 SOLD | 필수 |
| FR-41 | 결제 실패 처리 | 결제 실패 시 예약과 좌석 상태는 유지(HELD), 사용자 재시도 허용 | 필수 |
| FR-42 | 결제 상태 조회 | 결제 건의 처리 상태 조회 | 선택 |
| FR-43 | 환불 | CONFIRMED 예약 취소 시 결제 취소(모의) 처리 후 결제 상태 REFUNDED 기록 | 필수 |

### 2.6 알림

| ID | 기능명 | 설명 | 우선순위 |
|---|---|---|---|
| FR-50 | 알림 구독 | 로그인 사용자가 SSE(Server-Sent Events)로 서버와 연결을 맺고 실시간 알림을 수신 | 선택 |
| FR-51 | 대기 순번 실시간 갱신 | 대기 순번/활성 전환 상태가 바뀌면 서버가 SSE로 클라이언트에 전송 (FR-21 폴링 대체) | 선택 |
| FR-52 | 선점 만료 안내 | 선점 만료 1분 전, 만료 시점에 SSE로 안내 전송 | 선택 |
| FR-53 | 예약 확정 알림 | 결제 완료 시 SSE로 예약 확정 알림 전송 | 선택 |

## 3. 비기능 요구사항

| ID | 구분 | 설명 | 우선순위 |
|---|---|---|---|
| NFR-01 | 동시성 | 동일 좌석에 N명이 동시에 선점 요청해도 정확히 1건만 성공해야 함 (데이터 정합성) | 필수 |
| NFR-02 | 동시성 | 좌석 선점 로직은 분산락 또는 낙관적 락으로 보호하고, 부하 테스트로 검증 | 필수 |
| NFR-03 | 부하 제어 | 대기열을 통해 회차별 동시 활성 사용자 수를 제한(예: 회차당 100명) | 필수 |
| NFR-04 | 성능 | 좌석 조회 API 응답 시간 p95 500ms 이내 (부하 테스트 기준) | 선택 |
| NFR-05 | 신뢰성 | 선점 만료/좌석 복구는 서버 재시작 후에도 누락 없이 처리 | 필수 |
| NFR-06 | 보안 | 인증이 필요한 API는 인증 토큰 없이 접근 불가. 관리자 API는 ADMIN 권한 필요. 비밀번호는 해시 저장 | 필수 |
| NFR-07 | 관측성 | 주요 처리(선점 성공/실패, 만료, 결제)는 로그로 추적 가능 | 선택 |
| NFR-08 | 테스트 | 동시성 시나리오(다중 스레드 선점, 대기열 순서)에 대한 자동화 테스트 보유 | 필수 |

<br>

## 4. 제약사항

- Java 17, Spring Boot, PostgreSQL 16, Redis 사용
- 결제는 외부 PG 대신 모의 결제(Mock)로 처리
- 초기 배포 환경은 개인 Linux 서버, 이후 AWS 이전 예정

## 5. 검증 시나리오(수용 기준)

| 시나리오 | 기대 결과 |
|---|---|
| 좌석 1개에 100명이 동시에 선점 요청 | 1명 성공, 99명 실패 응답. 좌석 상태 HELD 1건 |
| 선점 후 5분 미결제 | 좌석 AVAILABLE 복구, 예약 EXPIRED, 재선점 가능 |
| 활성 정원 100명, 대기 300명 | 앞선 100명만 활성, 나머지는 순번 조회 시 대기 상태 |
| 활성 토큰 없이 선점 API 호출 | 401/403 거부 |
| 결제 성공 | 예약 CONFIRMED, 좌석 SOLD, 동일 좌석 재선점 불가 |
| 결제 실패 | 예약 HELD 유지, 좌석 HELD 유지, TTL 내 재시도 가능 |
| 활성 상태에서 10분 내 예매 미완료 | 대기열 토큰 만료, HELD 예약 EXPIRED, 좌석 AVAILABLE 복구, 활성 슬롯 반환 |
| CONFIRMED 예약 취소 | 결제 REFUNDED, 예약 CANCELLED, 좌석 AVAILABLE 복구 |
